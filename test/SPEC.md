What the automated tests cover. All scenarios run the real sync flow against throwaway on-disk projects (a temp directory with a lockfile, a fabricated `node_modules/`, and optional pre-existing skills directories), plus a few direct checks of skill naming, content hashing, and Git-symlink-support detection.

Covered, by area:

- **Project-root resolution** — a missing lockfile and a missing `node_modules/` are usage errors; the run walks up from a monorepo workspace package to the workspace root; a Yarn Plug'n'Play project does nothing and exits 0.
- **Skill-package enumeration** — only packages with the `use-npm-skills` keyword count (including scoped `@scope/name` packages); a marked package with no skill layout, a `SKILL.md` without a frontmatter name, and an invalid skill name are each skipped with a warning.
- **Materialization** — the root-`SKILL.md` layout materializes only that file while the `skill/` layout materializes the directory's full contents (nested files included); the materialized directory is named after the frontmatter name, not the package name; `source.json` records package, version, layout, and content hash; a skill-name collision keeps the alphabetically first package and warns; an update replaces changed content and removes stale files; a version-only bump rewrites only `source.json`; a second run is idempotent (up-to-date, exit 0).
- **Target skills directories** — with no qualifying directory, `.agents/skills/` is created and used (an existing empty skills directory does not qualify); an existing skills directory containing a skill is used instead; root-level `skills/` and one-level-deep `*/skills/` are discovered while deeper nesting is not; with several targets, real files land in `.agents/skills/` and the others get relative per-skill symlinks; a directory-level symlink collapses targets into one physical directory with nothing mirrored.
- **Existing structure wins over the default** — an existing per-skill symlink pattern keeps its primary directory; an existing duplicated-copies pattern leads to copies everywhere; on Windows, copies are the default without Git symlink support and symlinks with it, and an existing symlink pattern wins even without support; a skills directory added later gets its mirror symlinks on the next run.
- **Tamper protection** — a locally modified skill is left untouched with the exact promised warning and exit 1; an added file counts as a modification; CRLF-only differences do not; `--force` without a terminal lists the modified skills and overwrites them (exit 0); a declined confirmation keeps the changes (exit 0); other skills still sync when one is tampered.
- **User-authored skills win** — an existing skill without `source.json` is never touched and the packaged skill is skipped with a warning.
- **Pruning** — uninstalling a package deletes its pristine skill together with its mirror symlinks; a locally modified orphan is adopted (`source.json` removed, files kept, exit 0); an adopted skill blocks re-materialization when the package comes back.
- **Config file** — `exclude` skips the package and prunes its pristine skill, or adopts a modified one; `skillsDirs` overrides discovery (first target alphabetically becomes primary); invalid JSON and a `skillsDirs` entry outside the project are usage errors; unknown keys warn.
- **Git-symlink-support detection** — a repository whose Git `core.symlinks` setting is disabled or unset reports support as unavailable; enabled (where symlinks can be created) reports it as available — checked against throwaway Git repositories, isolated from the machine's own Git configuration.
- **Skill naming and hashing invariants** — frontmatter-name extraction (quoted values, byte-order mark, CRLF, frontmatter at end-of-file, absent or nested `name`); skill-name validation (accepted and rejected shapes); content hashing is file-order-independent, normalizes CRLF to LF for text, leaves binary content untouched, and distinguishes file paths from file contents.
