What the automated tests cover. All scenarios run the real sync flow against throwaway on-disk repositories (a temp directory with a `.git` entry, a fabricated `node_modules/` — plain, or laid out like pnpm's virtual store — and optional pre-existing skills directories), plus a few direct checks of package-link recognition, content hashing, and Git-symlink-support detection. Symlink mode is the default; scenarios about copy mode opt into it through the config file.

Covered, by area:

- **Project-root resolution** — no `node_modules/` under the root is a usage error; the run walks up from a workspace package to the Git repository root, which is the root even when the lockfile and `node_modules/` live in a subdirectory (the links then point into that subdirectory's `node_modules/`); outside a Git repository the nearest lockfile's directory is the root, and without one the working directory is; a Yarn Plug'n'Play project does nothing and exits 0.
- **Skill enumeration** — a `skills/` directory with at least one subdirectory is the only marker: a package with one counts regardless of keywords (scoped `@scope/name` packages included), while a package with only a keyword, a root `SKILL.md`, a single `skill/` directory, a `skills/` directory holding only files, or a `skills/` directory without a `package.json` beside it is silently not a skill package; skill packages installed in a workspace package's own `node_modules/` are found at any depth (and linked from there) while a `node_modules/` nested inside a package is not crawled, a repository whose only `node_modules/` is a workspace package's still works, and a package present in several `node_modules/` counts once with the first copy that ships skills winning; a package shipping several skills has each materialized on its own; every subdirectory of `skills/` is materialized as-is without warnings — one without a `SKILL.md`, one whose frontmatter `name` differs from the directory name, one with no frontmatter, and one with an unconventional directory name included — while files directly in `skills/` are ignored.
- **Symlink mode** — each skill is a relative symlink to its `skills/<name>/` directory inside the package, exposing exactly that directory (package files outside it are not visible, and there is no `source.json`); the entry is named after the skill, not the package; the link goes through the package's top-level `node_modules/` entry, never pnpm's versioned store path, so repointing the package at a new version (as an update does) shows the new content without a run and the next run reports the skill as up-to-date; a link found pointing at the versioned path is re-pointed to the stable one; a skill-name collision keeps the alphabetically first package's link and warns; a second run is idempotent; with several skills directories each gets its own link; a directory-level symlink collapses targets into one physical directory; a skills directory added later gets its links on the next run; copies and mirror symlinks left from copy mode are replaced by links; on Windows, links are the default with Git symlink support and copies (with a notice) without it.
- **Target skills directories** — with no qualifying directory, `.agents/skills/` is created and used (an existing empty skills directory does not qualify); an existing skills directory containing a skill is used instead; root-level `skills/` and one-level-deep `*/skills/` are discovered while deeper nesting is not; a directory holding nothing but package links, dangling ones included, qualifies.
- **User-authored skills win** — an existing skill directory without `source.json`, or a symlink of the user's own to content of their own, is never touched and the packaged skill is skipped with a warning; user content blocks the skill only in the skills directory where it stands, the other directories still get their links.
- **Pruning (symlink mode)** — uninstalling a package removes its links from every skills directory, reported once with the directories; a skill dropped by a new version of its package has its link removed while its sibling skills stay; a skills directory left with nothing but dangling links is still pruned; a hand-made link into a package under another name is left alone while the package provides the skill it points at, and removed once the package is gone.
- **Copy mode** — the full contents of the skill's `skills/<name>/` directory are copied (nested files included) and package files outside it are not; `source.json` records package, version, and content hash, one per skill of a multi-skill package; an update replaces changed content and removes stale files; a version-only bump rewrites only `source.json`; a second run is idempotent; links left from symlink mode are replaced by copies. Mirroring: with several targets, real files land in `.agents/skills/` and the others get relative per-skill symlinks; a directory-level symlink collapses targets into one physical directory with nothing mirrored; an existing per-skill symlink pattern keeps its primary directory; an existing duplicated-copies pattern leads to copies everywhere; on Windows, copies are the default mirror style without Git symlink support and symlinks with it, and an existing symlink pattern wins even without support; a skills directory added later gets its mirror symlinks on the next run.
- **Copy mode: tamper protection** — a locally modified copy is left untouched with the exact promised warning and exit 1; an added file counts as a modification; CRLF-only differences do not; `--force` without a terminal lists the modified skills and overwrites them (exit 0); a declined confirmation keeps the changes (exit 0); other skills still sync when one is tampered. Switching to symlink mode: a modified copy stays (warning, exit 1) while a pristine one becomes a link, and `--force` replaces the modified copy by a link.
- **Copy mode: pruning** — uninstalling a package deletes its pristine copy together with its mirror symlinks; a locally modified orphan is adopted (`source.json` removed, files kept, exit 0); an adopted skill blocks re-materialization when the package comes back; a skill dropped by a new version of its package is removed while its siblings are updated.
- **Config file** — `exclude` removes the excluded package's links (every skill of a multi-skill package); `skillsDirs` overrides discovery, every listed directory getting its link; `mode: "copy"` produces copies, and any other `mode` value is a usage error; invalid JSON and a `skillsDirs` entry outside the project are usage errors; unknown keys warn. Copy mode: `exclude` adopts a modified copy, and with `skillsDirs` the first target alphabetically becomes the primary directory.
- **Package-link recognition** — a symlink whose target has the shape `node_modules/<package>/skills/<skill>` is a package link naming its package and skill, dangling or not, scoped packages and pnpm's versioned store paths included; a symlink to a sibling skills directory, to a package's root or `skills/` directory, or deeper into a skill, a real directory, and a missing path are not.
- **Git-symlink-support detection** — a repository whose Git `core.symlinks` setting is disabled or unset reports support as unavailable; enabled (where symlinks can be created) reports it as available — checked against throwaway Git repositories, isolated from the machine's own Git configuration.
- **Hashing invariants** — content hashing is file-order-independent, normalizes CRLF to LF for text, leaves binary content untouched, and distinguishes file paths from file contents.
- **Package hooks** — `install-package` installs only its package's skills (linking to the stable path, also when run from pnpm's virtual store) and reports, without touching them, another package's skill that is missing (in any of several skills directories), left over from an uninstalled package (the dangling link stays), or whose link points elsewhere; an updated package is nothing to report, its link being in sync whatever version is installed; a bad state exits non-zero only under CI; user-authored content in the way, excluded packages, and name-collision losers are not reported; an excluded package installs nothing but still checks the others; a package the crawl does not see installs nothing; a working directory without a `package.json` is a usage error. Copy mode: an outdated copy, another package's locally modified copy and its own, and a missing mirror symlink are reported. `uninstall-package` removes its package's links from every skills directory and nothing else; in copy mode it removes pristine copies with their mirror symlinks and adopts modified ones.
